# Harness specification registry (`harness_spec.py`)

## Boundary / responsibility

`agent-scripts/harness_spec.py` is the single declarative source of truth for
per-harness metadata that more than one tool needs to agree on: the canonical
harness name list, the CLI binary name, the human install hint, the process
basename used for claim liveness, and the instruction-file discovery facts
(expected filenames, fallback probe paths, the load-bearing set, and the probe
token sets). Before this module each consumer kept its own hand-maintained copy
of some subset of those lists, and the copies drifted — most visibly
`gen_interfaces.HARNESS_DIRS` omitted `codex` (5 entries) while the rest of the
repo carried 6, so the generated command matrix and doc-discovery silently never
saw codex. The registry makes "add a 7th harness" a one-place edit and turns the
drift itself into a testable invariant.

It is stdlib-only, import-safe (no top-level side effects), and immutable:
`HarnessSpec` is a frozen dataclass, the registry is a plain `dict` keyed by name
whose authoring order is the canonical render order, and every derived view
(`ALL_NAMES`, `HARNESS_BASENAMES`, `LOAD_BEARING_NAMES`, `DISCOVERY_TARGETS`) is
an ordered `tuple` precisely because several consumers render these lists and a
reordering would change generated bytes.

## Key interfaces

- `HarnessSpec` (frozen dataclass) — one record per harness; `process_basename()`
  falls back to `name` so claim detection never assumes `name == basename`.
- `HARNESSES: dict[str, HarnessSpec]` — the registry; also the import-order
  contract for render order.
- Ordered views + accessor helpers (`binary(name)`, `install_hint(name)`, …) that
  the dict-keyed consumers use instead of local literals.
- Consumers (in-scope, migrated): `gen_interfaces.py`, `install.py`,
  `link_inspect.py`, `dev_status_mutation.py`, `harness_discovery_check.py`,
  `gen_shell_completion.py`.
- Consumer (deferred): `gen_skills.py` — its render surface is 35 template tokens
  fed largely by per-skill `SKILL_PARAMS`, not a per-harness fact table, so it
  keeps `CAPABILITY_TABLE` until a later item maps the tokens explicitly.

## Explicit non-goals

- Does not absorb `gen_skills` generation/token machinery (that would leak
  generation concerns into install-time code).
- Does not replace `gen_shell_completion.py`'s adapter dataclass with
  `HarnessSpec` directly; `gen_shell_completion.py` defines `HarnessAdapter` to
  avoid name collision and derives its `cli` facts from the registry.
- Is not a runtime plugin system, package registry, or schema framework — a small
  ordered fact table plus derived views.

## Known unknowns / deferred decisions

- `pi-prompt` is a synthetic `gen_skills`-only alias mirroring pi's facts; when
  gen_skills is migrated, the invariant becomes "gen_skills harness set ==
  registry ∪ {pi-prompt}", so the parity test must special-case it.
- Whether any harness ever has `process_name != name` is unexercised today
  (defaults to `name`); the field exists so codex's inclusion is a data decision,
  not a hidden assumption.
- The `expected_root` token *strings* stay fixture-internal constants in
  `harness_discovery_check.py`; only the per-harness *sets* that reference them
  move to the registry, keeping the import direction one-way (discovery →
  registry).
